# Контроль мотивації Ласки

API: `/api/motivation`. Потрібні чинний Bearer JWT та вибрана компанія `x-tenant-id: laska` (для менеджера без заголовка використовується його власна компанія). Доступ мають лише backend-ролі `admin` і `manager` Ласки. Супервайзер, агент та бренд-менеджер не отримують доступу до загального порівняння команди.

## Зберігання

Модуль використовує чинний `getPool('laska')` і `LASKA_NEON_URL`. Нових секретів або з’єднань із фірмою ОлгаТорг для даних мотивації не потрібно. Автентифікація залишається штатною для SODA.

При першому авторизованому зверненні ідемпотентно створюються дві окремі таблиці у поточній схемі PostgreSQL:

- `motivation_state`: актуальний JSON стану та номер ревізії;
- `motivation_history`: незмінювані через API знімки, час, дія та email користувача з серверної сесії.

Користувач БД має мати `CREATE TABLE` у цій схемі. Таблиці продажів і довідників не змінюються. Операції збереження стану та історії виконуються однією транзакцією. Якщо ревізія застаріла — HTTP 409, жодного перезапису або запису аудиту. Помилка аудиту також відкочує зміну стану.

Початковий стан — 10 слотів агентів, порожні результати, умовний бюджет 15000 грн та буфер 7 днів. Це налаштування тесту, не реальні результати чи затверджена виплата. Дані попереднього Sites автоматично не читаються: їх можна експортувати та імпортувати через інтерфейс SODA.

## Маршрути

- `GET /state` → `{data, revision}`.
- `POST /state` → тіло `{data, revision, action}`; відповідь `{revision, history}`. До 10000 записів; JSON-запити до 8 МБ. Весь імпорт перевіряється до початку транзакції.
- `GET /history?before=<revision>` → до 100 записів, від нових до старих; cursor `before` для наступної сторінки.
- `GET /history/:id` → метадані та знімок `data` відповідної ревізії.

Схема валідації: `src/modules/motivation/motivation.domain.js`. Статус «підтверджено» вимагає факту, цілі >0, відповідального та джерела. Відсутні числа інших статусів зберігаються як `null`, не нулі. Перевіряються календарні дати, унікальність ID, прив’язка агентів, погоджений строк та буфер.

Стан зберігається знімками; історію потрібно враховувати в плануванні обсягу БД. Цей модуль призначено для ручного пілоту 10 агентів, а не імпорту рядків продажів.

## Перевірка

```sh
node --test test/motivation.test.js test/dailySales.test.js
```

Тести перевіряють права, ізоляцію компаній, підтвердження, некоректний імпорт, транзакції, конфлікт ревізій та відкат при помилці аудиту. Вони використовують тестовий пул; production PostgreSQL цими тестами не змінюється.

Рекомендований порядок випуску: backend, потім frontend. Після випуску увійти менеджером/адміністратором у Ласку та відкрити «Контроль мотивації». Якщо БД не дозволяє створення таблиць, API поверне помилку; інтерфейс не підставляє демонстраційні результати.
